# Железный Стяг — правила для ИИ-помощников

Игра про наёмный отряд в средневековой Европе: карта кампании и бои отрядов в реальном времени. Проект на Godot 4.7 в папке `godot/`. Пишут Глеб, Захар и Викентий, каждый со своим ИИ. Этот файл читают Claude Code, Codex, Cursor и другие; общие правила и уроки лежат в **`shareness/`**.

## Прочитай перед работой
1. `shareness/README.md` — как устроена общая память и как её пополнять.
2. `shareness/lessons.md` — решения владельца и грабли, на которые уже наступали.
3. Нужный навык из `shareness/skills/*/SKILL.md`: `build-and-test`, `git-flow`, `changelog`, `graphics`, `godot-module-placement`, `unit-parts`.
4. `godot/docs/README.md`, затем [Blueprint](godot/docs/architecture/BLUEPRINT.md), [план миграции](godot/docs/architecture/MIGRATION.md) и [правила разработки](godot/docs/architecture/DEVELOPMENT.md). Соблюдай границы `modules.json`, требования `requirements.json` и ADR. Изменение архитектурного контракта требует ADR и автоматической проверки.

## Жёсткие правила
- **В `main` напрямую не пушим — никто, ни люди, ни ИИ.** Каждая задача — в своей ветке, ветки пушит кто угодно, в том числе ИИ без спроса. В `main` изменения попадают только через Pull Request; сливает Глеб.
- **Сначала issue, потом код — всегда, перед любой работой над проектом.** Порядок:
  1. Поищи похожие issues — и открытые, и закрытые: `gh issue list --state all --search "<ключевые слова>"` (или REST: `gh api "search/issues?q=repo:akglebak16/iron-standard+<слова>"`). Ищи по нескольким словам и синонимам, не только по точному названию.
  2. Есть открытая такая же или очень похожая задача и её никто не делает (нет назначенного, нет открытого PR и свежей ветки под неё) — бери её, не плоди дубль. Её уже делают — не начинай параллельно, спроси Глеба.
  3. Есть закрытая такая же или очень похожая задача — не делай вслепую: уточни у Глеба, что не так (вернулся баг, сделано не так, нужно доделать) и стоит ли открыть её заново или завести новую со ссылкой на старую.
  4. Ничего похожего нет — создай issue (что сделать и зачем, коротко), потом ветка и PR.
  В описании PR обязательно строка `Closes #N` (или `Fixes`/`Resolves`): GitHub сам закроет issue при слиянии в `main`, руками не закрываем. Без неё не пройдёт локальная проверка PR (`pr_check.cjs`).
- **Один issue — один PR.** Каждая задача (issue) делается в своей ветке и уходит отдельным Pull Request с `Closes #N` в описании. Не собирай несколько задач в один PR: такой PR сложно проверить, откатить и описать в релизе. Мелкая сопутствующая правка (тест, урок, документация к этой же задаче) — в тот же PR; всё остальное — отдельным.
- Каждое изменение для игрока описываем в PR в разделе «## Для игрока» (шаблон подставит его сам). Из этих разделов собираются [Releases](https://github.com/akglebak16/iron-standard/releases).
- **Проверка PR — локально, и ИИ запускает её сам (#255).** CI на GitHub для PR выключен: у приватного репозитория кончается бюджет Actions. Вместо него — `node godot/tools/pr_check.cjs <Godot>`: те же шаги и тот же выбор тестов, что были в CI (тесты инструментов, архитектура против базы, Godot-тесты по изменениям, сборка и release-smoke; правки только в `godot/docs/*.md` и вне `godot/` — без Godot), плюс проверка строки `Closes #N`. Скрипт ставит на коммит головы PR статус `local/pr-check` и обновляет в PR комментарий «Локальная проверка». Порядок для ИИ — без напоминаний от человека:
  1. Работа над PR закончена (всё закоммичено, ветка запушена, PR открыт с `Closes #N`) — **сам** запусти `pr_check.cjs`. Не говори «готово» и не зови Глеба на слияние до прогона.
  2. Красное — чини и запускай снова. Проверку не валит только тест, который красный и на `main` и по которому открыт issue: `--known-red=tests/…/test_x.gd#N`.
  3. Godot на машине нет (облако) — всё равно запусти: пройдут архитектура и тесты инструментов, на PR уйдёт «⏳ нужен прогон на Windows». Есть терминал на Windows-ПК человека (например, ПК Глеба через device_bash) — прогони там сам. Нет — в конце ответа прямо напомни одну команду: ветка, `node godot/tools/pr_check.cjs <Godot>`.
  4. Новый пуш в PR — новый прогон: статус привязан к коммиту.
  Сливаем PR только с зелёным `local/pr-check` на последнем коммите. Красные тесты в `main` не отправляем, проверки не отключаем.
- **FPS не роняем.** Тяжёлую логику (ИИ, поиск пути, шаг мира, сохранение) не считаем в кадре главного потока: симуляция мира идёт в рабочем потоке ([ADR-024](godot/docs/architecture/ADR-024-world-simulation-thread.md)), главный поток только рисует. В `_process` и `_draw` — никаких циклов по всему миру с выделением памяти, глубоких копий и обращений к каталогу на каждый кадр: считай один раз и запоминай. Правка, которая трогает карту, бой или их отрисовку, замеряется до и после (`view_benchmark.gd`, как в `shareness/lessons.md`); фриз или просадка против `main` — это поломка, такой PR не отправляем.
- **Интерфейс не ломаем и держим в одном стиле.** После любой правки, которая может задеть экран, гоняй тесты интерфейса (`godot/tests/integration/app/`: `test_ui_smoke`, `test_visual_interface`, `test_ui_feedback` и тест затронутого окна) и смотри изменённые экраны на снимке окна: ничего не съехало, не обрезано, не налезает, текст помещается. Новое окно, кнопку или панель собирай из уже существующих элементов и по образцу соседних экранов: те же шрифты, цвета, рамки, отступы и выравнивание по сетке. Свой стиль «с нуля» не изобретаем; к новому экрану добавляй тест.
- **Сохранения не ломаем.** Правка, которая меняет данные мира, героя или отряда, обязана загружать сейвы, сделанные до неё: новое поле получает значение по умолчанию, старое не исчезает молча. Проверь загрузкой старого сейва и тестами сохранений.
- **Проверяй в самой игре.** Перед пушем запусти сцену, которую трогал (или тест, который её действительно загружает, из `godot/tests/integration/app/`): зелёные модульные тесты не ловят ошибку разбора в сцене.
- **Баланс попутно не трогаем.** Числа (урон, цены, скорость, сила и размер отрядов, награды) меняем только в задаче про баланс и пишем об этом в «## Для игрока».
- **Чужую работу не переписываем молча.** Правка задевает модуль, который недавно делал другой автор, — напиши в PR, что и зачем изменил; большую переделку сначала согласуй.
- **Тексты для игрока — на русском и в серьёзном тоне.** Никаких заглушек, английских строк и технических названий в интерфейсе; новые строки клади так, чтобы их можно было перевести (#110).
- **PR держим небольшим.** Крупную задачу режь на части, каждую из которых можно проверить и откатить отдельно: под каждую часть свой issue и свой PR.
- Браузерная JS-версия удалена, мультиплеера пока нет. Возвращать мультиплеер (сеть, сервер) — только по решению и с участием Глеба.
- Только бесплатные внешние ассеты; по умолчанию графику и звук делаем сами. Источник и лицензию записываем в `godot/docs/ASSETS.md`.
- Запрещено портить и ломать игру: не удалять и не обнулять механики, фракции, карту, сохранения и тесты, не вставлять мусор, вредоносный код или обход правил. Сломал — чини сам или откати.
- Концепцию игры без согласия Глеба не меняем. Большие переделки в духе игры можно (новая механика, фракция, режим, переработка экономики или боя) — коротко предупреди Глеба. Нельзя то, что меняет игру целиком: другая эпоха и сеттинг (огнестрел, техника), другой жанр, отказ от боёв отрядами в реальном времени и от карты Европы, шутовской тон вместо серьёзного. Такое — только после явного «да» от Глеба.
- Сомневаешься, меняет ли правка концепцию или ломает ли что-то — не делай, спроси Глеба.

## Самообучение (обязательно)
Узнал что-то полезное для всех (причина бага, неочевидное ограничение, приём, решение владельца) — в конце задачи допиши короткий пункт в `shareness/lessons.md` и закоммить вместе с изменением. Повторяемая процедура из нескольких шагов — новый навык в `shareness/skills/<имя>/SKILL.md`. Устаревшее правь, а не копи рядом.
