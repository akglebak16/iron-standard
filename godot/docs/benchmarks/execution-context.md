# Окружение измерения

2026-11-15 один и тот же Windows release exe, contact 1000×1000, seed 4242,
60 warmup + 180 measured ticks, profile-phases:

| Запуск | simulation p95, мс | snapshot p95, мс |
|---|---:|---:|
| sandbox, 1 | 71.440 | 11.985 |
| sandbox, 2 | 79.601 | 13.358 |
| sandbox, 3 | 75.372 | 12.029 |
| host, 1 | 35.454 | 5.203 |
| host, 2 | 31.737 | 4.561 |

Состав и счётчики событий совпали. Позднее два последовательных запуска
одной сборки на хосте дали 80.263 и 35.093 мс. Поэтому объяснение разброса
только sandbox оказалось недостаточным; механизм вариативности ещё не установлен.
Смешивать эти распределения в регрессионном сравнении нельзя.
Performance-приёмка запускается на хосте; sandbox пригоден для функциональных
проверок. Ни частота CPU, ни схема питания при сравнении не менялись помощником.
Это короткая диагностика, не приёмка FPS и не утверждённый baseline.

Дополнительная диагностика после spatial workspace: Windows сообщил шесть
SMT-ядер класса эффективности 1 (маска `0x0fff`) и четыре ядра класса 0
(`0xf000`). Больший EfficiencyClass обозначает более производительные ядра
согласно [контракту Windows](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-processor_relationship).
Временный launcher ограничил только себя и дочерние процессы, затем восстановил
affinity; системный план питания остался прежним.

| Ограничение запуска | simulation p95, мс | snapshot p95, мс |
|---|---:|---:|
| P-ядра, 1 | 33.787 | 4.637 |
| P-ядра, 2 | 32.527 | 4.662 |
| E-ядра | 77.864 | 12.601 |

Это подтверждает чувствительность benchmark к размещению на P/E-ядрах;
конкретное ядро каждого прежнего тика не записывалось, поэтому его задним
числом не определяем. Отчёты `spatial-reuse-*-diagnostic.json` сохраняют
ограничение запуска. `spatial-reuse-unrestricted-release.json` содержит оба
неограниченных результата, включая медленный. Игровая приёмка должна пройти
с обычным планировщиком; быстрый диагностический прогон её не заменяет.

`release.cjs` теперь пишет `<exe>.build.json`: SHA ревизии и содержимого исходников
(включая новые файлы), SHA самого exe со встроенным PCK, дату, успешный smoke.
`benchmark.cjs` проверяет этот файл и по умолчанию отвергает устаревшую сборку.
Для намеренного сравнения старого артефакта есть `--allow-stale-build`; отчёт
сохраняет идентичность именно сборки, а не текущего checkout.
Запуск обязательно помечается `--execution-context=host` или `sandbox`.
`unspecified` сохранён для совместимости, такой отчёт не годится для приёмки.

Характеристики эталона зафиксированы в `reference-windows.json`. Проверка
привязки артефакта: `node godot/tools/build_identity.test.cjs`.
