# Бой на C++: замер фаз тика и план переноса, 20 ноября 2026

Задача #261, часть зонтика #250. Цель — понять, куда уходит время тика боя 1000×1000, прежде чем переносить
что-то на C++. Код игры не менялся. Данные всех повторов — [battle-native-plan-2026-11-20.json](battle-native-plan-2026-11-20.json).

## Условия

- AMD Ryzen 7 5700X, Windows 10, Godot 4.7.2 из Steam (та же машина, что в [Р0а](terrain-r0a-2026-11-18.md) и
  [Р1а](terrain-r1a-2026-11-19.md); с отчётами на i5-14400F числа напрямую не сравнивать).
- Код `main` `de53b56`. Release-сборка `node godot/tools/release.cjs` (smoke прошёл). В отчёте `dirty=true`
  только из-за перевода строк в `*.import`, код тот же.
- Без параллельных сборок и тестов.
- Команда:
  `node godot/tools/benchmark.cjs dist/godot/migration-release/IronStandard.exe --n=1000 --scenario=<…> --ticks=3600 --warmup=120 --seed=4242 --profile-phases --repeat=5 --execution-context=host`.
- Сценарии `tests/performance/battle_benchmark.gd`:
  - конница — `cavalry`, плотные блоки;
  - смешанный — `mixed`, половина пехоты, треть стрелков, остальное конница;
  - стрелки — `volley`;
  - лес на фланге — `mixed --terrain=edge`;
  - малый бой — `mixed --n=200`.
- В каждой клетке — медиана пяти повторов. Счётчики событий в повторах одного сценария совпали.
- Доля — это доля среднего фазы в среднем тике. p95 фаз не складываются в p95 тика.

## Что входит в фазы

Описание фаз в #250 неточное, поэтому сначала по коду (`session.gd`, `movement.gd`):

| Фаза | Что в ней | Где считается |
|---|---|---|
| `commands_interpolation` | приказы игрока, копия прежних позиций для сглаживания | C++ `capture` |
| `tactics_siege` | мозги сторон (`tactics.gd`), герой ведёт свои отряды, доктрины отрядов (`squad_doctrine.gd`), перестроение, осада | GDScript, решения по расписанию |
| `hero` | управление героем | GDScript |
| `ai_movement_combat` | пакет ядра (`movement_kernel.hpp`): выбор цели, план, движение. На каждом ударе, натиске и уходе с поля ядро возвращается в GDScript: `Charge.hit`, `CombatStep.advance_unit` → `Combat.strike` и `shoot` → `State.hurt` и `kill` (урон, блок, мораль от удара, события). **Урон ближнего боя живёт здесь**, а не в `contacts` | C++ и обратные вызовы в GDScript |
| `contacts` | расталкивание бойцов (ADR-011) — не урон | C++ |
| `projectiles` | полёт стрел и попадания (`resolve_projectiles`, `Combat.arrow_hit` → `hurt`, укрытие лесом) | GDScript, кандидаты ищет C++ |
| `morale_result_events` | мораль раз в секунду (`Morale.advance`) и подкрепления, итог боя, сбор событий | GDScript |
| `storage_compaction` | уплотнение строк погибших (`State.compact_inactive`) | GDScript и C++ `copy_rows` |
| `movement_index` | индекс эталонного пути GDScript; на native-пути фазы нет | — |

## Что внутри дорогих фаз (диагностика)

Временные отметки профиля стояли только в копии и не коммитились. Прогоны — те же сценарии, по три повтора.
Отметки добавляют около 0,1 мс к тику. Подфазы считаются только по тикам, где они были: проверка морали —
раз в секунду, уплотнение — когда кто-то погиб.

**`ai_movement_combat`** — среднее за тик, мс:

| | Конница | Смешанный | Стрелки |
|---|---|---|---|
| Вся фаза | 1,99 | 1,19 | 0,84 |
| Вызовы ядра C++, всего | 1,61 | 1,05 | 0,77 |
| Вызовов ядра за тик (среднее / p99) | 14,4 / 30 | 5,7 / 18 | 3,9 / 16 |
| Самый дешёвый повторный вызов ядра | 0,073 | 0,090 | 0,087 |
| Обратные вызовы: удар / натиск | 0,22 / 0,18 | 0,14 / 0,07 | 0,10 / — |
| `State.hurt` с `kill`: время / попаданий за тик | 0,16 / 6,0 | 0,09 / 2,7 | 0,21 / 4,3 (в основном стрелы) |

**Урон на GDScript дешёвый.** Обратные вызовы удара и натиска вместе с `hurt` стоят 0,2–0,4 мс за тик.

**Дорог сам выход из пакета.** Ядро возвращается в GDScript на каждом ударе и натиске: 6–14 раз за тик, в
плотной сшибке до 30. На каждом выходе `movement_adapter.cpp` заново проверяет все 2000 строк. Проверка идёт
через `PackedInt64Array::operator[]` и `PackedVector2Array::operator[]`, а в godot-cpp это вызов в движок
через указатель на функцию на каждый элемент: около 14 вызовов на строку, ~28 000 на каждый выход из пакета.

**Проверка гипотезы.** Та же проверка, но через `ptr()`, на той же диагностической сборке:

| | Конница: до → после | Смешанный: до → после |
|---|---|---|
| p95 тика | 6,28 → 4,59 | 4,40 → 3,57 |
| среднее тика | 3,09 → 2,19 | 2,33 → 1,92 |
| p99 тика | 7,67 → 5,57 | 8,02 → 7,36 |
| `ai_movement_combat`, среднее | 1,99 → 1,15 | 1,19 → 0,83 |
| самый дешёвый повторный вызов ядра | 0,073 → 0,028 | 0,090 → 0,046 |

Счётчики событий, число измеренных тиков и живые бойцы в конце совпали со сборкой `main`: бой тот же. Это
часть 2 плана.

**Мораль: всплеск раз в секунду.** Проверка морали идёт раз в 60 тиков. В p95 тика её не видно, но она
держит p99 тика на 7,6–9,9 мс. Одна проверка стоит, мс:

| | Конница | Смешанный | Стрелки |
|---|---|---|---|
| Оценка поля для потерь отрядов (`FieldAssessment.assess`) | 2,22 | 2,76 | 1,79 |
| Проход по бойцам, в том числе бегство (`_rout_step`) | 1,28 | 1,99 | 3,83 |
| Паника и перестроение собравшихся отрядов | 0,29 | 0,36 | 2,47 |
| **Всего за проверку** | **≈3,8** | **≈5,1** | **≈8,1** |

**Уплотнение хранилища** — за тик, где кто-то погиб, мс:

| | Конница | Смешанный | Стрелки |
|---|---|---|---|
| Проход по строкам (`compact_inactive`) | 0,24 | 0,26 | 0,31 |
| `copy_rows` в C++ | 0,28 | 0,33 | 0,35 |
| Фильтры списков лямбдами (`_visible_units`, `group.units`) | 0,34 | 0,41 | 0,43 |
| Пересборка индексов | 0,00 | 0,00 | 0,00 |

`copy_rows` дорог по той же причине, что и выход из пакета: в `column_adapter.cpp` номер строки
`rows[k]` читается через `operator[]` внутри цикла по 44 полям. Это около 88 000 вызовов в движок на одно
уплотнение. Так же написан и `render` — подготовка снимка для отрисовки: p95 снимка 1,1–1,6 мс.

## Выводы

1. Дороже всего не урон, а граница между GDScript и C++. Поэлементный доступ godot-cpp к packed-массивам в
   адаптерах съедает 0,4–0,9 мс среднего тика в бою 1000×1000. Это чинится в двух файлах адаптеров, без
   изменения поведения, контракта колонок и ядра.
2. Мораль — главный всплеск: 4–8 мс одним тиком раз в секунду. Больше половины — оценка поля и проход по
   бойцам в GDScript.
3. Уплотнение хранилища — 0,25–0,37 мс в среднем и 1,2 мс p95. Треть — `copy_rows` (пункт 1), ещё треть —
   фильтры лямбдами.
4. Урон и обратные вызовы — 0,2–0,4 мс. Стрелы у стрелков — 0,30 мс в среднем и 1,07 мс p95.
5. `contacts` — уже C++, 0,47–0,53 мс. Решения отрядов (`tactics_siege`) — 0,05–0,13 мс, по расписанию.
   Их не трогаем.
6. Малый бой 200×200 укладывается с большим запасом: 0,74 мс p95.

**ADR.** Части 2 и 5 контракт не меняют: колонки и правила остаются у ядра боя, меняется только то, как
адаптер читает массивы. Части 3 и 6 меняют владельца правил (мораль и урон уходят в ядро, события и Unit —
производные). Перед ними нужен ADR с автоматической проверкой в `architecture.cjs`, по образцу ADR-019.
