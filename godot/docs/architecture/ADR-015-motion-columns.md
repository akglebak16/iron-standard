# ADR-015: авторитетные координаты и скорости

`MotionStore` хранит координаты и скорости активных юнитов в packed-колонках.
Unit.position/velocity обращаются к строке battle_index; отдельное значение
существует только до добавления в бой и после архивации. При стабильном
уплотнении строка копируется, handle переносится, затем меняется battle_index.
Архивированная запись отсоединяется до освобождения строки.

Native solver получает эти колонки и возвращает новые packed-массивы;
присваивание хранилищу заменяет прежний цикл копирования в каждый Unit.
GDScript contact solver пишет в то же хранилище. Остальные контактные колонки
(радиус, масса, сторона, live/fleeing) пока являются производными входами,
которые заполняются перед контактной фазой. Snapshot по-прежнему отделяет данные.

Это начало авторитетного SoA. HP, мораль, боевые таймеры и холодные данные
пока принадлежат Unit; внутренний фасад свойств нужен существующим правилам.
Нельзя на основании этого этапа объявлять BATTLE-SOA-HANDLES завершённым.
Стоимость фасада проверяется отдельно, а не считается бесплатной.

Первый вариант увеличил p95 тика до 30,540–30,747 мс. Причина на уровне
реализации: пространственные запросы многократно вызывали getter позиции.
Production-индекс теперь читает заимствованную packed-колонку напрямую и
обновляет её при synchronize после замены буфера native-адаптером. Отдельный
тест меняет весь массив, сохраняя число строк, и проверяет новые ячейки.

Холодные определения снимка индексируются стабильным history_index; столбцы
однократно получают нужную ёмкость, затем заполняются по индексу. Определение
героя заменяется целиком, чтобы смена оружия не меняла уже выданные снимки.
Срок жизни снимка по-прежнему определяется потребителем; буфер не переиспользуется.

Короткий release diagnostic (seed 4242, contact 1000×1000 + герой,
60 warmup/180 measured ticks, два повтора, P-core affinity 0x0fff):

| Вариант | Tick p95, мс | Snapshot p95, мс |
| --- | --- | --- |
| Первоначальный фасад | 30,540 / 30,747 | 5,744 / 5,521 |
| Прямые чтения колонок | 25,918 / 23,560 | 5,456 / 5,351 |
| Колонки + ёмкость снимка | 23,299 / 22,522 | 3,233 / 3,314 |

Исходные отчёты: `docs/benchmarks/motion-facade-initial.json`,
`motion-direct-intermediate.json`, `motion-columns-pcore.json`. Они включают
SHA исходников, exe и DLL. Это последовательные короткие диагностические
замеры разных сборок, не рандомизированный сравнительный эксперимент.
Целевые 6/1 мс не выполнены; 60 секунд × пять повторов и графическая
приёмка остаются обязательными. У этих замеров прогрев выполнял только
симуляцию; снимки прогревом ещё не охвачены — это ограничение методики.

Проверены все 91 Godot test files, architecture gate с отрицательными fixtures,
Windows release-smoke. Fingerprints поля/осады совпадают с прежними значениями.

Последующее устранение повторных чтений: steering, центры сторон, радиус
влияния смерти и предыдущие позиции читают motion-колонки напрямую.
Оси построения кэшируются до изменения direction; проверка наличия живых
бойцов и centroid группы больше не создают временный отфильтрованный массив.
Изменение центра/слота не кэшируется. Проверка смены направления и повторного
возврата к прежнему углу закрепляет инвалидацию; fingerprints сохранены.

`formation-hotpath-pcore.json`: short release sampling v2, contact 1000×1000,
60/180 ticks × два повтора, P-ядра. Tick p95 21,632/22,428 мс, snapshot
3,188/3,430 мс. Во время второго прогона выполнялся короткий статический
architecture check; эти данные диагностические и не являются контролируемым
A/B-экспериментом. Порог 6 мс по-прежнему не достигнут.
