# Технический этап после переноса одиночного боя

Этот документ сохраняет результаты прежнего технического этапа. Карта и кампания уже реализованы; повторно переносить их по старому порядку ниже не нужно. Текущий обязательный план — [Blueprint migration](../../architecture/MIGRATION.md), паритет механик — [чек-лист](../../../MIGRATION_CHECKLIST.md).

## Порядок работы

1. **Зафиксировать исходное состояние.** Прогнать тесты Godot и сохранить эталонные кадры полевого боя и осады. Замерить время запуска и время кадра в одинаковых сценах и настройках. Использовать эти проверки после каждого изменения.
2. **Проверить подход с ассетами на двух примерах.** Заменить одну процедурную музыкальную дорожку на аудиоассет. Собрать осадную стену из повторно используемых визуальных элементов Godot, привязанных к сегментам и проходам симуляции. Сравнить качество, удобство авторских правок и производительность. Для внешних материалов записывать источник, лицензию, условия указания автора и право использования в коммерческом релизе.
3. **Выделить подтверждённое переиспользование.** Проверить границы ниже. Делить крупные функции по ответственности, например на выбор поведения, подготовку данных и вывод. Сохранять игровые правила и проверять поведение тестами. Перенос папок делать отдельным коммитом, если проверка границ покажет, что он упростит навигацию.
4. **Закрепить результат.** Обновить [архитектуру Godot](../../../ARCHITECTURE.md) для разработчиков, Claude и Codex. Описать владельцев данных, направления зависимостей, размещение кода, ассетов и тестов. Обновить проверки границ модулей, повторить исходные замеры и проверки, затем перейти к карте мира.

## Что проверять на переиспользование

| Область | Кандидат на общий технический код | Ответственность игрового модуля |
| --- | --- | --- |
| Звук и музыка | Воспроизведение, шины, громкость, затухание и переходы между дорожками | Бой, карта и меню выбирают темы и определяют, когда они звучат |
| Графика | Композиция слоёв и кэширование при общем контракте, например между боем и экраном экипировки | Бой определяет анимацию, оформление поля и стены. Экипировка владеет данными предметов. Инвентарь определяет их отображение |
| ИИ | Оценка вариантов действий при наличии общего алгоритма и реальных потребителей | Бой выбирает цель и момент отступления. Кампания управляет движением отрядов и дипломатией |

Аудиофайлы, изображения, сцены и ресурсы Godot — основной кандидат для контента, который авторы редактируют вручную. Код остаётся для реакций на события, композиции экипировки и вариаций поля по `seed`.

`apps/godot/composition/` остаётся точкой сборки. Прежнее предложение о gameplay/infrastructure заменено утверждёнными core/runtime/adapters из Blueprint; допустимые зависимости определяет только docs/architecture/modules.json.

## Результаты

### Шаг 1. Исходное состояние

Эталонные кадры, замеры и команды повтора лежат в [`../../../tools/baseline/README.md`](../../../tools/baseline/README.md). На том историческом этапе прошли 53 теста Godot; это не число текущего набора.

### Шаг 2. Проверка подхода с ассетами

Оба примера сделаны рядом со старым кодом и переключаются одним флагом, чтобы их можно было сравнить. Журнал источников и лицензий — [`../../../ASSETS.md`](../../../ASSETS.md).

**Музыка.** `BattleMusic` играет зацикленный `battle_theme.ogg`, а если файла нет или `BattleMusic.use_theme_asset = false`, возвращается к прежнему процедурному голосу. Реакции на события боя остались в `combat_audio.gd`.

| | Процедурная дорожка | Аудиоассет |
| --- | --- | --- |
| Правки автором | Менять числа в коде (шкала, интервалы) | Заменить файл или перерисовать партитуру в скрипте; мелодия и ритм уже заданы нотами, а не случайны |
| Память и CPU | Банк PCM собирается при запуске (8 голосов нот, 7 барабанов, эхо считается в коде) | Один поток OGG ~0,4 МБ, декодируется движком, на каждый тик ничего не считается |
| Качество | Случайные ноты шкалы, каждый бой звучит иначе | Фиксированная мелодия 16 тактов, звучание не зависит от seed |

Дорожку я прослушать не мог, оценил только по цифрам (громкость, шов петли). Послушайте её в бою или осаде (клавиша N включает музыку) и решите, оставлять ли её по умолчанию.

**Осадная стена.** `WallSceneView` собирает стену из сцен `terrain/wall/` (сегмент, башня, створка ворот): текстуры и размеры правятся в редакторе, а симуляция задаёт только прямоугольники сегментов и проёмы. Обломки в проёмах остаются кодом, потому что раскладываются по seed. `TerrainView.use_wall_scenes = false` возвращает старую отрисовку кодом.

| | Рисунок кодом (`WallView`) | Сцены и текстуры (`WallSceneView`) |
| --- | --- | --- |
| Правки автором | Цвета и размеры константами, рисунок только по коду | Текстуры меняются файлами, оформление в сцене; код трогать не надо |
| Вид | Линии шва чёткие при любом зуме камеры | Тот же рисунок; швы чуть мягче, потому что 1-пиксельные линии текстуры масштабируются |
| Время кадра (осада, программный рендер) | ~48–50 мс | ~47–48 мс, различия в пределах шума |
| Запуск | без изменений | без изменений (~0,4 с до готовности сцены в обоих вариантах) |

Что пригодится дальше: тайлинг делает `TextureRect` в режиме «тайл», а `Sprite2D` с областью дальше края текстуры в этом рендерере повторяет не весь рисунок; для текстуры с однопиксельными линиями фильтр `nearest` теряет линии при нецелом зуме камеры, нужен линейный.

### Шаг 3. Переиспользование и крупные функции

**Переиспользование.** Подтверждённых вторых потребителей у звука, графики и ИИ нет: всё это используется только боем (проверено поиском по `godot/`). На этом этапе общие модули не создавались; текущие условия выноса и таблица решений находятся в [`../../../ARCHITECTURE.md`](../../../ARCHITECTURE.md), раздел «Общий технический код: когда выносить».

**Крупные функции** поделены по ответственности без смены порядка RNG и побочных эффектов:

| Функция | Что выделено |
| --- | --- |
| `core/battle/application/factory.gd: create` (85 строк) | `_resolve_companions`, `_spawn_companions`, `_create_hero` |
| `core/battle/application/session.gd: snapshot` (68) | `_unit_values`, `_camera_target`, `_shot_values`, `_wall_rects`, `_wall_defense_values` |
| `core/battle/rules/siege_defense.gd: step` (62) | `_muster`, `_step_stones`, `_step_cauldrons`, `_step_fires` |
| `core/campaign/economy/battle_loot.gd: collect` (66) | `_summarize_enemy`, `_gear_odds` |

Поведение проверено отпечатком `tools/behavior_fingerprint.gd` (хеши полного снимка каждые 120 тиков и итога для демобоя и осады): строки до и после идентичны. Для добычи отдельным прогоном по 300 seed получен тот же результат.

### Шаг 4. Закрепление

- Обновлён `ARCHITECTURE.md`: дерево модулей с `wall/`, `audio/assets/` и `tools/`, раздел об ассетах, решения о переиспользовании и порядок рефакторинга без смены поведения.
- `tests/architecture/test_boundaries.gd` теперь проверяет и сцены/ресурсы (`.tscn`, `.tres`), а не только скрипты.
- Повтор исходных замеров: 53 теста зелёные; симуляция 300 на 300 — 18–21 мс/тик (было 20–25), 24 на 24 — 1,0–1,2 мс; кадры поля и осады совпадают с эталоном (кадр 300 — 0,00%, кадр 1500 — до 1%, в пределах шума эффектов); время кадра ~41 мс (поле) и ~49 мс (осада).
