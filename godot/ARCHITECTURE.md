# Архитектура Godot-версии

Обязательные правила для Claude, Codex и других разработчиков. Браузерный `src/` остаётся эталоном поведения до полного переноса; подробный учёт переноса по файлам и функциям — в `MIGRATION_CHECKLIST.md`, сводка боя — в `battle/PARITY.md`. Архитектурный рефакторинг не является переносом новых механик.

## Главный принцип

[Технический план после паритета одиночного боя](battle/POST_PARITY_PLAN.md) задаёт порядок проверки ассетов и общих модулей перед переносом карты мира.

Игра организована по владельцу игровых правил, внутри — по ответственности. Симуляция работает без сцены, клавиатуры и файлов. Сцена получает готовую сессию, отправляет команды и рисует снимок. Владельцем состояния запущенного боя является сессия; вторую независимую сессию можно создать в том же процессе.

```text
godot/
  project.godot
  app/                    # composition root: загрузить, собрать, внедрить, запустить
    main.gd, main.tscn
    encounter_aftermath.gd # передаёт завершённый результат в правила кампании один раз
  campaign/               # состояние отряда и правила мира после встречи
    world/                # генерация карты Европы (чистая симуляция, без сцен и файлов)
    presentation/         # картинка карты: шейдеры земли, рельеф, реки; читает campaign/world
    data/                 # товары и параметры наград встречи
    rules/                # применение потерь, здоровья и наград к отряду
    economy/              # трофеи и вместимость обоза
    tests/                # rules/, economy/
  ASSETS.md               # журнал источников и лицензий файловых ассетов
  tools/                  # общие проверки: test.cjs, behavior_fingerprint.gd, baseline_capture.gd, baseline/
  tests/architecture/     # зависимости между игровыми модулями
  troops/                 # определения бойцов для боя, найма и мировой карты
    config.gd             # устойчивые категории пехоты, стрелков и конницы
    data/                 # catalog.gd, troops.json
    tools/                # export_troops.cjs
    tests/data/           # проверка каталога независимо от боя
  equipment/              # предметы, слоты и свойства типов урона
    config.gd             # типы урона, классы брони, свойства щитов
    data/                 # gear_catalog.gd, items.json
    rules/                # hero_gear.gd, damage_type.gd
    tools/                # export_gear.cjs
    tests/                # data/, rules/
  characters/             # перки, определения и профили спутников
    config.gd             # устойчивые коды атрибутов и предел ранга
    data/                 # perk_catalog.gd, companion_catalog.gd и JSON
    rules/                # perk_effects.gd, companion_profile.gd
    tools/                # export_perks.cjs, export_companions.cjs
    tests/                # data/, rules/
  battle/
    config.gd             # именованные общие параметры и коды правил боя
    application/
      factory.gd          # новый runtime из сценария + проверенного каталога
      session.gd          # команды, порядок тика, жизненный цикл, снимок
      hero_input.gd       # типизированные значения управления героем
    model/
      state.gd            # состояние, группы, приказы, инварианты урона и смерти
      unit.gd, group.gd    # сущности с устойчивыми ID и изменяемыми полями
    rules/
      movement.gd         # движение и разрешение столкновений
      targeting.gd        # выбор цели с приоритетами и таймером
      ai_decision.gd      # режим и точка движения бойца
      spatial_index.gd    # общий пространственный индекс для крупных боёв
      combat_step.gd      # атака отдельного бойца и разрешение снарядов
      combat.gd           # разрешение удара, блока, выстрела
      charge.gd           # конный натиск в режиме атаки
      damage.gd           # расчёт урона после брони
      result.gd           # итог одиночного боя для будущей кампании
      hero_control.gd     # правила управления героем
      morale.gd           # периодический расчёт морали и бегства
    data/
      battle_setup.gd    # схема Resource для редактора
      demo_battle.tres    # состав армий, seed, герой конкретной встречи
      army_builder.gd     # превращение определений в новые runtime-сущности
      companion_builder.gd # создание бойца ИИ из проверенного профиля
      hero_stats.gd       # адаптер экипировки к боевому Unit
    presentation/
      scene.tscn, view.gd # ввод, камера, HUD, рисунок
      demo_config.gd      # временные визуальные параметры и тексты
      terrain/           # шейдер поля, осадная стена и текстуры растений
        wall/            # сцены и текстуры стены (сегмент, башня, створка), правятся в редакторе
      audio/             # звуки событий и музыка; assets/ — файлы дорожек
      companion_dialogue.gd # реплики по снимку и событиям боя, пузыри и журнал
    tests/                # application/, model/, rules/, data/, presentation/, fixtures/
    tools/                # измерение производительности, скрипты рендера ассетов (battle_theme, wall_*.png)
```

Ищи сначала владельца игрового правила, затем роль. Тесты живут с владельцем: валидация предметов — `equipment/tests/data/`, их влияние на боевой урон — `battle/tests/rules/`, сборка героя из предметов — `battle/tests/application/`. Новые крупные области получают такую же структуру по мере появления кода. Не создавай пустые каталоги заранее. Подроль (`rules/movement/`) нужна, когда у неё несколько связанных файлов, а не ради дополнительного уровня. Один общий `config.gd` и документы модуля могут оставаться в его корне.

## Выбор модуля перед каждой правкой

1. Найди в `src/` определение правила и **всех его потребителей**. Папка исходного JS-файла или текущий экран Godot не определяют владельца. Спроси, какое состояние и какой инвариант меняются: состав войск, экипировка, конкретный бой или состояние мира.
2. Помести общее определение и чистое правило к владельцу. Потребитель хранит только адаптер к своему runtime. Поэтому `equipment/rules/hero_gear.gd` рассчитывает слоты без ссылки на боевого Unit, а `battle/data/hero_stats.gd` применяет результат к Unit. `troops/data/catalog.gd` не знает о сессии боя.
3. Проверь направление зависимостей: `app → battle/campaign → troops/equipment/characters`. `troops`, `equipment` и `characters` не зависят от `battle` или `campaign`; `battle` и `campaign` не зависят друг от друга напрямую. Их связывает `app` через явные входные данные и результат. Не делай глобальный `shared`, `utils`, `managers` или общий модуль ИИ для несвязанных правил.
4. Новый верхний модуль создавай, когда у области есть собственные данные/инварианты и как минимум один реальный потребитель, а размещение в существующем модуле вызвало бы обратную зависимость или дублирование. Начни с минимальных папок по фактическим файлам. Если второй потребитель появился позже, перенеси правило к владельцу в отдельном проверенном рефакторинге.
5. В одном модуле держи реализацию и её проверки. Сквозной тест принадлежит модулю сценария: проверка покупки и участия предмета в бою будет в `campaign/tests/` или `app/tests/`, а тест формулы пробития — в `equipment/tests/rules/`.

### Карта браузерной игры для следующего переноса

| Исходники и правила | Владелец в Godot | Почему |
| --- | --- | --- |
| `01_core.js` — `TROOPS`, категории, свойства войск | `troops/` | Бой, набор, содержание и мировой ИИ читают одни определения |
| `01b_gear.js` — `EQ`, слоты, `dtPierce`/`dtMul` | `equipment/` | Бой, торговля, инвентарь и экран героя используют одни предметы и формулы |
| `03_battle.js`, `03b_gore.js` — шаг боя, боевой ИИ, столкновения и эффекты | `battle/` | Эти правила живут только во встрече; боевой ИИ остаётся `battle/rules/` |
| `05_world.js`, `05g_war.js` — карта, движение партий, дипломатия, войны, осады на карте | будущий `campaign/` с `world/`, `war/` и локальным ИИ по необходимости | У них общий мир и цикл времени, отдельно от одной боевой встречи |
| `05d_trade.js`, `06b_inventory.js` — рынок, сделки, провизия, обоз | будущий `campaign/economy/` и его UI; чистые свойства предмета — `equipment/` | Сделка меняет золото/инвентарь мира, но читает общий каталог предметов |
| `01c_perks.js`, `05e_comps.js` — развитие героя и спутников | `characters/` для профиля, навыков и перков; найм и движение — `campaign/` | Бой получает проекцию профиля и навыков, а кампании принадлежат размещение и найм |
| `02_art.js`, `04_audio.js`, `05b_worldart.js`, `06_*.js` — рисунок, звук и интерфейс | `presentation/` соответствующего игрового модуля; общие ассеты только после второго использования | Визуальный код не должен владеть симуляцией |

Разные виды ИИ не образуют модуль сами по себе. `battle/rules/ai_decision.gd` оперирует Unit, целью и дистанцией в бою; будущий ИИ карты оперирует партиями, дипломатией и путём в `campaign/`. Общий чистый алгоритм выделяй только после фактического повторного применения и общего контракта.

## Зависимости и владение

Тексты спутников хранятся в каталоге `characters/data/companions.json`. Фабрика выдаёт сцене отделённый словарь реплик по ID бойцов, допущенных к встрече. Таймеры, выбор фраз и отдельный генератор случайных чисел принадлежат `battle/presentation/`. Диалоги читают снимок и события, поэтому не меняют ход симуляции.

1. `app/main.gd` загружает каталоги из `troops/` и `equipment/` и сценарий, вызывает фабрику боя, внедряет сессию через `view.configure(session)` **до** `add_child`. Ошибка сборки останавливает запуск. Боевых формул здесь нет.
2. `battle/application/factory.gd` создаёт отдельные State, Unit и RNG для каждого боя. Необязательный `hero_profile` сценария проецируется через `equipment/rules/hero_gear.gd` и `characters/rules/perk_effects.gd`, а `battle/data/hero_stats.gd` применяет параметры к Unit при создании и смене оружия; пустой профиль оставляет прежнего героя превью. `app` загружает и внедряет каталоги войск, вещей и перков; бой не читает файлы. Сессия хранит копию профиля для переключения оружия. Resource — описание, его нельзя менять во время боя и нельзя хранить в нём HP, таймеры, ссылки на живые сущности. Загруженные Resource могут разделяться движком между сценами.
   Начальное `Group.layout(true)` сортирует бойцов по убыванию ранга и затем по `troop_id`; одинаковые типы сохраняют порядок создания по `Unit.id`. Обычное перестроение использует текущую поперечную позицию, не исходный тип.
   `ArmyBuilder` назначает `enemy_leader_name` первому врагу наивысшего ранга, а начальную мораль определяет свойство войска с приоритетом над бонусом лидера. Сценарий передаёт бюджеты фигур каждой стороны. Для прежних сценариев стандартный бюджет берётся из таблицы совместимости в `battle_setup.gd`.
3. `companion_profiles` содержит весь состав спутников. `characters/rules/companion_profile.gd` разрешает сохранённые значения поверх каталога, определяет допуск в бой и ранг навыков. Фабрика передаёт в сессию сумму `surv` всех спутников, а `CompanionBuilder` создаёт только допущенных бойцов до расстановки и бонусов героя. Снаряжение и личные перки проходят через те же адаптеры, что у героя. Статус спутника не включает ручное управление и эффекты с условием `isHero` исходника.

   `application/session.gd` принимает значения управления и приказы; внешние клиенты не получают State или Unit. Передача State в конструктор передаёт сессии право изменения: вызывающий не использует сохранённую ссылку для параллельных изменений. В GDScript `_field` — соглашение, не защита языка.
4. `set_hero_input` копирует значения. `issue_order` валидирует и ставит приказ в FIFO-очередь; `true` означает принятие, а не успешное применение к непустой группе. Приказы применяются в начале следующего положительного тика. Управление героем хранит последнее принятое состояние до следующего обновления.
5. Порядок тика: **приказы → тактика сторон и следование герою → перестроение групп → управление героем → для каждого бойца выбор цели/режима, поворот и атака до перемещения → столкновения и границы поля → полёт/попадание снарядов → мораль → исход**. `Movement.step` вызывает `CombatStep.advance_unit` внутри прохода при переданном RNG; `CombatStep.resolve_projectiles` запускается после столкновений. Отдельный `CombatStep.step` нужен для изолированных тестов правил атак. Смерть героя переводит сессию в промежуточное `HERO_DOWN`, бой продолжается; разгром определяется на тике морали, финальный исход фиксируется после 2,2 с. Изменение порядка считается изменением поведения и требует проверки паритета. Завершённая сессия больше не принимает действия и не продвигает время.
6. `snapshot()` возвращает отделённые значения: рисунок не может изменить симуляцию через полученные массивы/словари. Это проекция для HUD и графики, **не формат сохранения и не полный replay**. View читает её один раз за физический тик и повторно использует при рисовании. После задержанного завершения `result()` возвращает отдельную копию итогов для будущей кампании; до завершения возвращает пустой словарь. По завершении боя обновления прекращаются.
7. `battle/rules/` работает с типизированными моделями, RNG и аргументами. Формулы не знают про UI, перевод, Node, Input, FileAccess и application. `battle/model/` не зависит от data/application/presentation; допускается вызов чистой формулы (`Damage.after_armor`) без обратной зависимости. Урон и смерть остаются методами State, чтобы «Последний рубеж», лечение за убийство и мораль применялись совместно. `equipment/rules/` не зависит от моделей боя и состояния мира.
8. `troops/data/`, `equipment/data/` и `characters/data/` загружают и проверяют определения; неуспешная замена сохраняет прежний каталог. Полученные определения и переданные исходные словари не разделяют изменяемые ссылки с каталогом. `battle/data/` адаптирует их к боевым моделям. Это ещё не полная схема будущей экономики и модов.
9. `presentation/` использует только публичное API application и общие коды config. Не загружает каталог и не обращается к моделям/правилам напрямую. Обращения к `$Camera` и `$Hud` допустимы: это собственные узлы сцены.
10. `app/encounter_aftermath.gd` один раз передаёт итог готовой сессии в `campaign`. Правила обновляют копии отряда и мира, сопоставляя противника по ID, а `app` передаёт сводку в демосцену. Трофеи рассчитываются после потерь и пополнения провизии. RNG наград создаётся отдельно при сборке встречи. Демо хранит результат в памяти. В рабочей кампании эти данные должен принять владелец мира.
11. `campaign/data/encounter_rewards.gd` сопоставляет вид встречи с параметрами её последствий. `battle_quests.gd` применяет прогресс и награды, `relations.gd` обновляет отношения и возвращает изменения враждебности для будущего журнала.
12. `campaign/rules/siege_aftermath.gd` собирает гарнизон и укрывшихся лордов для встречи и применяет итог к тому же поселению по ID. Генерация состава по фракции и качеству принадлежит `troops/rules/generation.gd`, а размеры армий и набор по типу поселения задаёт кампания. Вызывающий сохраняет созданный гарнизон в мире перед запуском боя.
13. `battle/data/siege_setup.gd` создаёт стену и задаёт центры защитников до расстановки. `battle/model/siege_wall.gd` хранит геометрию, а движение разрешает контакт со стеной после парных столкновений и границ арены. Представление получает копию прямоугольников стены через снимок.
14. При осаде сессия вызывает `Tactics.siege_step` вместо полевой тактики. Движение ИИ запрашивает ближайший подходящий проход перед рулением. Укрытие считается после проверки блока, по точке запуска снаряда и позиции цели при попадании.
15. `AiDecision` передаёт исходную дистанцию до цели в фазу атаки. Натиск может сдвинуть цель, но не меняет исходную дистанцию текущего решения. Завершение замаха проверяет актуальную дистанцию. Бегство проверяет выход с поля до перемещения, а контакт со стеной разрешается после парного расталкивания и до ограничения границ поля.
16. Снимок снаряда содержит точку пуска, точку попадания, долю полёта и вид. `presentation/projectile_view.gd` строит по этим значениям видимую дугу и тень. Проекция не передаёт ссылку на стрелка, а видимая высота не участвует в попадании.
17. Боевые правила записывают факты в очередь текущего тика. `Session.take_events()` передаёт последний пакет один раз. Следующий тик заменяет непрочитанный пакет. События содержат только значения и не расходуют RNG; HUD решает, какие сообщения и эффекты показать.
18. Сцена передаёт тот же пакет событий в `battle/presentation/audio/combat_audio.gd`. Банк PCM создаётся один раз, а готовые потоки используются ограниченным пулом проигрывателей. Шум генерируется отдельным RNG. Частота событий и расстояние до камеры регулируют воспроизведение без влияния на симуляцию.
19. Сигнал приказа записывается после применения к непустой группе. Тактика публикует оповещения при переходах, а сессия сообщает об исходе при его определении, до задержки экрана результатов. Оповещения без позиции имеют полную громкость.
20. `battle/presentation/audio/battle_music.gd` выбирает ноты и барабан отдельным RNG и играет зацикленный `assets/battle_theme.ogg`; если файла нет или `BattleMusic.use_theme_asset = false`, выбирает ноты и барабан сам и воспроизводит готовые PCM с затухающим эхом. `app/presentation_preferences.gd` хранит звуковые и визуальные флаги в `user://audio.cfg`, а сцена получает значения через `configure` и передаёт изменения сигналами.
21. `battle/presentation/impact_effects.gd` использует свой RNG, числовой стиль цели и отделённые события. Событие гибели несёт тип попадания, долю нанесённого урона и копию внешности цели. Выбор отделяемых частей, фонтаны и анимация полёта принадлежат отображению. Буферы осевших частей и отметок земли перезаписывают старые записи при достижении лимита.
22. `unit_art.gd` растрирует тело и оружие один раз для каждого сочетания внешности и палитры. `unit_view.gd` использует отделённые значения снимка и события для замаха, вспышки и падения. Отрисовка отсекает фигуры вне камеры. Состояние анимации не записывается в Unit.
23. `app` передаёт сцене `seed` и `biome` сценария. `battle/presentation/terrain/` получает размеры поля и сегменты стены из начального снимка. Слой земли под эффектами использует шейдер без времени, а стена строит команды рисования один раз. Расположение проёмов следует из сегментов симуляции. `WallSceneView` собирает стену из сцен `terrain/wall/` (сегмент, башня, створка), а обломки по `seed` остаются кодом; `TerrainView.use_wall_scenes = false` возвращает прежнюю отрисовку `WallView`.
24. `battle/data/vegetation_setup.gd` воспроизводит раскладку растений браузера по `seed` и границе осады. Сессия отдаёт сцене отделённую раскладку один раз. Движение проверяет стволы после стены и перед ограничением поля и обновлением пространственного индекса. Слой отображения кэширует текстуры по варианту и рисует растения в порядке глубины вместе с живыми бойцами.
25. `battle/presentation/unit_markers.gd` рисует метки по отделённым полям снимка: доле здоровья, группе, имени спутника и признакам лидера и бегства. Выбор группы хранится в сцене и передаётся с приказом. Названия групп общие для HUD и журнала.
26. `battle/presentation/hud/` отвечает за миникарту, указатель врага и метку приказа. Миникарта повторно использует параметры материала земли и получает сегменты стены и бойцов из снимка. Для указателя снимок отдаёт центр боеспособных врагов и их численность с учётом веса фигур. Метку рисуем после события `ORDER_APPLIED` с исходной точкой команды удержания.
27. При смене оружия сессия определяет текущий слот по фактически экипированному предмету. Снимок отдаёт название предмета для HUD. События `WEAPON_SWAPPED` и `RANGED_WEAPON_UNAVAILABLE` различают успешную смену и отсутствие дальнего оружия. Слой отображения выбирает подпись, а щелчок звучит при успешной смене.
28. `battle/presentation/battle_camera.gd` владеет слежением, масштабом, ограничением по краям поля и визуальным дрожанием от событий `HIT`. Сессия задаёт цель слежения по живым войскам после ранения героя. Прицел, точка приказа и упреждение используют положение камеры без дрожания. Миникарта и отсечение фигур используют фактическое преобразование окна.
29. `battle/presentation/hud/battle_controls.gd` рисует состояние героя и групп из снимка и передаёт запросы сигналами. Сессия применяет запрос слота после замаха и обрабатывает выход из боя отступлением через обычный результат поражения. Пауза и темп принадлежат сцене. Темп меняет шаг симуляции, камера и музыка используют реальное время. Нажатие ЛКМ начинает атаку только после обработки GUI.
23. Событие `DOWN` наследует тип атаки от смертельного попадания. `impact_effects.gd` выбирает число и скорость брызг, ведёт рост луж и переносит созревшие лужи в общий ограниченный буфер земли. Герой и спутники получают обычные брызги при ранении. Отключение крови очищает лужи и брызги без изменения состояния боя.

Тест `tests/architecture/test_boundaries.gd` проверяет явные зависимости между слоями `battle` и модулями `troops`, `equipment`, `characters`, `app` и `campaign`. Также он ловит возврат прежних идентификаторов нежити в боевые правила. Новые обращения к ID контента проверяем при ревью.

## Ассеты: что файл, что код

Файлы Godot (аудио, картинки, сцены, ресурсы) — основной вариант для контента, который авторы правят руками; код остаётся для реакции на события, композиции экипировки и вариаций по `seed`.

- Ассет лежит у владельца: звук — `<модуль>/presentation/audio/assets/`, картинки и сцены — рядом с кодом, который их использует (`battle/presentation/terrain/wall/`). Общего каталога ассетов нет, пока не появился второй потребитель.
- Источник, лицензия, условия указания автора и право на коммерческий релиз записываются в [`ASSETS.md`](ASSETS.md) до коммита. Только бесплатные ассеты; по умолчанию делаем свои, скриптом из `battle/tools/` (результат всё равно можно править руками).
- `*.import` коммитим вместе с ассетом, `.godot/` — нет. `node godot/tools/test.cjs` перед тестами сам запускает импорт.
- Симуляция не знает про ассеты: сцена получает прямоугольники и события из снимка, файл задаёт только вид и звук. Ассет всегда имеет запасной путь в коде или флаг, который возвращает прежний вариант, пока владелец не подтвердил замену.
- Сцены в `presentation/` подчиняются тем же границам, что и скрипты: ссылаются только на свои ассеты и скрипты (проверяет `tests/architecture/test_boundaries.gd`).

## Общий технический код: когда выносить

Общий модуль появляется только после второго реального потребителя с общим контрактом. На сегодня подтверждённых нет, поэтому `shared`, `utils`, `infrastructure/` и общий ИИ не создаём.

| Область | Потребители сейчас | Решение |
| --- | --- | --- |
| Звук и музыка | Только бой (`battle/presentation/audio/`); `SoundBank` общий для эффектов и музыки внутри боя | Остаётся в бою. Шины, громкость и переходы между дорожками выносим, когда карта или меню начнут играть свою музыку |
| Графика | Только бой (`unit_art`, `detached_parts`, `terrain`); экрана экипировки и инвентаря в Godot пока нет | Остаётся в бою. Композицию слоёв и кэш выносим при втором потребителе (экран экипировки) с общим контрактом |
| ИИ | Только бой (`ai_decision`, `targeting`, `tactics`); ИИ кампании не написан | Остаётся `battle/rules/`. Общий алгоритм оценки вариантов — после второго сценария использования в кампании |

Группировку `gameplay/` для игровых модулей и `infrastructure/` для технических оцениваем при появлении первой общей технической подсистемы; до этого размещение прежнее, `app/` остаётся точкой сборки.

## Рефакторинг без смены поведения

1. Перед правкой запусти `godot --headless --path godot --script res://tools/behavior_fingerprint.gd` и сохрани вывод: он гоняет демобои и осаду на фиксированном seed и печатает хеши полного снимка (через каждые 120 тиков) и итога.
2. Дели функции по ответственности (выбор поведения, подготовка данных, вывод), порядок вызовов RNG и побочных эффектов сохраняй.
3. После правки повтори команду: строки обязаны совпасть, затем тесты, затем `battle/tools/benchmark.gd` и кадры `tools/baseline_capture.gd` (см. `tools/baseline/README.md`).

## Какие паттерны используем

| Подход | Решение и применение |
| --- | --- |
| DI и composition root | Ручная передача конкретных зависимостей через конструктор/`configure`. Контейнер и service locator сейчас не нужны. Заменяемую стратегию вводим, когда появляется второй реальный вариант. |
| OOP и композиция | Небольшие типизированные сущности и сервисы правил. Воин с конём, оружием и эффектами собирается из данных/способностей; иерархию `NordMountedEliteArcher` не создаём. |
| Разделение команд и чтения | Очередь приказов и запрос снимка; один источник состояния. Отдельные БД, CQRS-фреймворк, Event Sourcing и журнал всего тика не вводим. |
| Data-driven definitions | Сценарии — Resource, войска и предметы — проверяемые каталоги своих модулей. Runtime всегда отдельный. Идентификаторы стабильны и не зависят от отображаемого текста. |
| Strategy | Алгоритм выбора цели уже вынесен в `rules/targeting.gd`. Когда понадобятся разные тактики ИИ, добавляем стратегии с одинаковым контрактом вместо проверок конкретной фракции по всему движению. Сейчас одного алгоритма достаточно. |
| State machine | Outcome сессии оформлен enum. Для будущих взаимоисключающих фаз атаки/анимации вводим явные переходы и тесты. Текущие флаги ранения, бегства и блока нельзя механически свести в один enum: они могут сочетаться. |
| События и signals | Будущие редкие факты (`unit_died`, `battle_finished`) передаём от владельца UI/аудио. Сначала меняем модель, затем уведомляем. Пока потребителей нет, пустую шину событий не строим; сигнал на каждое перемещение бойца не нужен. |
| ECS, pooling, MultiMesh | Только по профилю и задаче. Не создаём Node на каждую формулу или снаряд. Пул требует полного сброса объекта; ECS не заменяет правильный алгоритм поиска соседей. |

Новое правило: сначала владелец правила по карте модулей, тест поведения и именованные параметры, затем минимальная реализация в его `rules/` или `data/` и вызов из потребителя в документированном порядке. Новый визуальный эффект: сначала определяем, какие значения/факты нужны представлению, затем расширяем проекцию или вводим событие; не выдаём наружу изменяемый Unit. Будущие сохранения: отдельный версионированный DTO с устойчивыми ID и миграциями, без сериализации SceneTree. Не выдаём текущий snapshot за готовую основу сетевой синхронизации.

### Как добавлять свойства контента

1. Найди все проверки ID войска, фракции, предмета, перка и спрайта, от которых зависит новая механика. Опиши само игровое свойство в данных владельца. Например, `troops/data/troops.json` задаёт `battle_traits` с базовой моралью, участием в проверке бегства, связью с лидером и реакцией на урон. ID по-прежнему нужны для поиска записи, сохранений и оформления.
2. Проверь схему при загрузке. В `battle/data/` перенеси проверенные значения в типизированные поля `Unit`. Значения по умолчанию должны сохранять текущее поведение для записей без свойства. Ключ связи с лидером сравнивается только внутри одной стороны, а вероятность задаётся для каждого связанного бойца. Сохраняй порядок обработки и расход RNG.
3. Правило читает свойство, например `morale_immune`, или получает явно выбранную стратегию при появлении двух разных алгоритмов. Различие в коэффициентах описывай данными. Новый интерфейс, подкласс или шина событий нужны лишь при конкретном потребителе и отличающемся поведении.
4. Проверь на синтетической записи с другим ID, что свойство можно повторно использовать без изменений правила. Добавь контроль для записи без свойства и сценарий со смешанным составом. Временные соответствия со старым форматом держи в экспортёре или адаптере. Для `battle_traits` источником генерации до завершения переноса служит `troops/tools/export_troops.cjs`.

Экипировка использует тот же принцип. Щит задаёт `projectile_block_bonus` отдельно от изображения. Для старых данных без этого свойства действует нейтральное значение, а экспортёр записывает исходный коэффициент для каждого штатного щита.

## Числа, тексты и соглашения

- `snake_case` для файлов/методов/полей, `UPPER_SNAKE_CASE` для констант, понятные имена единиц (`_seconds`, `_radius`, `_speed`). Скрипты подключаем явным `preload`; глобальные `class_name` добавляем только при необходимости регистрации типа в редакторе.
- Баланс встречи — `battle/config.gd`, классификация и свойства войск — `troops/config.gd` и `troops/data/troops.json`, свойства предметов и типов урона — `equipment/config.gd` и `equipment/data/items.json`. Конкретная встреча — `battle/data/demo_battle.tres`, временное оформление — `battle/presentation/demo_config.gd`. Каталоги сверяются с браузерным источником через `troops/tools/export_troops.cjs --check` и `equipment/tools/export_gear.cjs --check`. Новую настраиваемую величину помещаем к её владельцу, не дублируем в алгоритмах. Математические ноль/единица и индексы сами по себе не требуют констант.
- После переноса каждой механики обновляй `MIGRATION_CHECKLIST.md`: исходная функция/секция, статус, Godot-файл, тест и оставшиеся ветви. `battle/PARITY.md` — сводка, не замена подробному списку.
- Боевые коды и Outcome не являются строками перевода. Тексты пока русские временные; при переносе полноценного UI получат ключи локализации и TranslationServer. Строки диагностических ошибок предназначены разработчику.
- Внешние определения валидируем на границе, внутренние горячие циклы используют типы и уже проверенные данные. Новые публичные API указывают типы. Не обобщай зависимости до `Object`/`RefCounted`, если известен конкретный тип.
- Не мутируй базовую характеристику ради одного удара: передавай множитель/контекст расчёта. Модификатор последующих попаданий героя уже передаётся отдельным аргументом.
- Autoload с изменяемым состоянием боя, глобальный RNG, `get_tree()` из правил и межмодульные пути к чужим узлам не добавляем. Сеть и `server/` остаются зоной Глеба.

## Что проверено и где остаются ограничения

### Аудит архитектуры перед переносом спутников

Сверили зависимости и владение состоянием в `app`, `battle`, `troops`, `equipment` и `characters`, пути сборки героя и армии, порядок боевого тика, проекцию для сцены и покрытие тестами. Ручное внедрение сессии и каталогов соответствует [рекомендациям Godot по организации сцен](https://docs.godotengine.org/en/stable/tutorials/best_practices/scene_organization.html). Сценарий хранит данные, сессия управляет записью, правила тика работают вне дерева сцены. Отдельные модели записи и чтения потребуют обоснования конкретным потребителем.

| Риск | Статус и правило |
| --- | --- |
| Войско меняет поведение при смене фракции армии или арта | Исправлено. Мораль, связь с лидером и реакция на урон задаются данными. Бюджет фигур задаётся сценарием. |
| Два поля могут противоречить друг другу при создании спутника | Исправлено. Свойство `companion` вычисляется из `companion_id`. |
| Выбор цели и замах повторно ищут индекс через линейный обход | Исправлено. `State.add_unit` присваивает `battle_index`. Массив `State.units` дополняется и сохраняет порядок до конца сессии. Смерть и бегство меняют флаги, а порядок массива определяет разрешение совпадений. Тесты используют ID, отличающиеся от индексов. |
| Случайно запустить упрощённое движение вместо боевого шага | Исправлено. `Movement.step` требует RNG, а `step_formation_only` явно выделен для сравнения со старым эталоном. |
| Словари перков, оружия и снарядов переносят знание о полях через несколько частей боя | Осталось. При расширении каждого контракта выносить используемые поля в типизированную проекцию на границе, особенно при появлении нового потребителя. Порядок шага и вызовы RNG проверять отдельно. |
| Сцена читает конкретные клавиши | Осталось. При настройке управления перейти на InputMap до добавления второго расклада или поддержки геймпада. |
| Крупный бой расходует бюджет шага до отрисовки | Подтверждено замером ниже. Рабочий выбор целей всё ещё обходит бойцов при пересмотре цели, а попадания снарядов проверяют полный список. Измерять плотную схватку отдельно. |

Проверяем старые правила, сборку главной сцены, независимость двух сессий, одинаковое поведение при одинаковых входах/seed/dt, отсутствие обратной мутации через snapshot/каталог, очередь приказов, невалидные входы, остановку после победы и урон нескольких целей. Повторяемость проверена в одном движке с одинаковым шагом; это не гарантия межплатформенного lockstep. Полный паритет и все исходы игры ещё не достигнуты — см. PARITY.

На локальном Godot 4.7.2 debug/headless, 10 прогревочных и 60 измеряемых шагов по 1/60 секунды, обе армии из базовой пехоты атакуют (два запуска после переноса атак внутрь прохода по бойцам):

| Нагрузка | Симуляция, среднее | Снимок, среднее |
| --- | ---: | ---: |
| 24 против 24 + герой | 0,89–0,93 мс | 0,048–0,050 мс |
| 300 против 300 + герой | 16,00–16,16 мс | 0,675–0,684 мс |

Это короткий CPU-сценарий начала боя без графики/звука, не обещание FPS и не сравнение с экспортом release. Исторический замер до пространственного индекса: 143,33 мс на шаг 300×300; до изменения порядка атак после индекса: 32,56 мс. Текущий профиль отдельно измеряет движение вместе с атаками (13,83–14,06 мс для 300×300), затем снаряды (0,002–0,003 мс); прежнее деление фаз больше не соответствует коду. Для малого боя разница находится на уровне шума измерения/накладных расходов: проверять оба масштаба.

Индекс создаётся на тик при числе фигур от `SPATIAL_MIN_UNITS`; размер ячейки `SPATIAL_CELL_SIZE` в `battle/config.gd`. `Targeting.choose` с индексом (`SpatialIndex.best_target`) обходит кольца ячеек вокруг бойца и отсекает дальние ячейки по нижней границе взвешенного расстояния, а нынешнюю цель взвешивает первой. Результат и выбор при равенстве — как у линейного обхода. Расталкивание (`Movement._resolve_packed`) идёт по упакованным копиям позиций и мелкой сетке `battle/rules/collision_grid.gd` с запасом `COLLISION_SLACK`: порядок пар, арифметика `Vector2` и итог те же, что у простого цикла по всем парам. `AiDecision.plan_into` пишет решение в поля бойца без словаря. `tests/fixtures/legacy_movement.gd` и `legacy_combat_step.gd` — замороженные эталоны; `test_spatial_index.gd` сравнивает изолированные вызовы, а `test_spatial_full_battle.gd` — полный бой с ИИ с индексом и без него, побитово. `Movement.use_index` выключают только в таких сверках.

Сцена боя шагает раз в кадр, шаг ограничен 1/30 с, как `battleUpdate` в браузере, поэтому тяжёлый бой замедляется, а не копит догоняющие тики. В окне с несколькими ядрами шаг и снимок считаются в `WorkerThreadPool`, пока рисуется прошлый кадр (`view.gd`: `_worker_step`, `_to_session`). Без окна (тесты, инструменты) всё идёт в одном потоке; тесты вызывают `_physics_process` сами и ставят `frame_driven = false`. Улёгшиеся трупы и следы на земле один раз впечатываются в текстуру поля (`battle/presentation/ground_bake.gd`), как в браузере в `B.gg`. Кольца под бойцами — заранее нарисованные текстуры, порядок по глубине — нативная сортировка упакованных ключей, облик бойца кэшируется по id.

Замеры на одной машине (`battle/tools/benchmark.gd`, `battle/tools/view_bench.gd`, `node` с серверной загрузкой `src/`): JS считает шаг 300×300 за ~1,1 мс. Godot на GDScript — 15–17 мс на шаг и ~6 мс на снимок. С нативным ядром (ниже) — ~0,95 мс на шаг, 0,5 мс на снимок для сцены, ~1,5 мс на рисование рядовых бойцов.

### Нативное ядро боя (GDExtension)

Горячие циклы боя написаны на C++ в `native/` (godot-cpp, ветка 4.5) и подключаются через `battle_core.gdextension`; готовые библиотеки лежат в `bin/` для Windows, Linux и macOS (universal). Без библиотеки проект не запустится: `battle/model/unit.gd` наследует нативный `BattleUnit`, где хранятся поля бойца, которые читает ядро.

- `BattleCore.step` — весь шаг `Movement._step` (цели, решения ИИ, натиск, шаг, удары и выстрелы, расталкивание, стены, деревья). Правила, которые живут в GDScript (`Charge.hit`, `CombatRules.strike/shoot`, `battle.launch_projectile`, `wall.route/constrain`), ядро вызывает обратно, поэтому урон, события и RNG остаются там же.
- `BattleCore.frame_stats`, `unit_values`, `frame_values`, `render_data` — сводки и данные снимка. `render_data` — упакованный `PackedFloat64Array` по 12 чисел на бойца (порядок полей описан в `battle_core.cpp`); по нему рисуют `UnitPainter`, мини-карта и реплики спутников. `snapshot(true)` для сцены переиспользует словари рядовых бойцов (их подвижные поля устаревают), обычный `snapshot()` всегда даёт свежие отвязанные словари.
- `UnitPainter` рисует рядовых бойцов, кольца, полоски здоровья и растения в порядке глубины прямо в canvas item; героя, спутников, командиров и падающие тела рисует GDScript (`unit_view.gd`).

GDScript-правила остаются эталоном. `NativeSwitch.on` (и `Movement.use_native`) переключает ядро; `battle/tests/rules/test_native_core.gd` гоняет одни и те же бои обоими путями и сверяет снимки и бойцов бит в бит, а `render_data` — со словарями снимка. Поэтому ядро собирается без fast-math и без слияния умножения со сложением (`-ffp-contract=off`), а порядок операций повторяет GDScript. Меняешь правило боя — меняй обе версии и запускай этот тест.

Обращение к `Dictionary` из C++ идёт через интерфейс движка и стоит около микросекунды: в горячих местах ядро читает упакованные массивы и поля `BattleUnit`, а не словари.

Сборка: `cmake -S godot/native -B build -DGODOT_CPP_DIR=<godot-cpp> -DCMAKE_BUILD_TYPE=Release && cmake --build build --config Release`, библиотека попадает в `godot/bin/`. Workflow `.github/workflows/godot-native.yml` собирает все три платформы на каждое изменение `godot/native/`; их артефакты (`gh run download <id>`) коммитятся в `godot/bin/` тем же PR.


Сценарий измерения воспроизводим: `godot --headless --path godot --script res://battle/tools/benchmark.gd`. Время не является pass/fail-тестом на разных машинах. Перед оптимизацией сохраняем профиль и корректность; после — повторяем ту же нагрузку и отдельно проверяем плотную схватку, стрелы и бегство.

## Проверки и коммиты

Из корня репозитория: `node godot/tools/test.cjs <путь-к-godot.exe>` (сначала импортирует ассеты), `node godot/troops/tools/export_troops.cjs --check` и `node godot/equipment/tools/export_gear.cjs --check`. Проверка каталога ожидаемо обнаружит намеренное изменение баланса. Runner выявляет зависание и ошибки скриптов даже при коде выхода 0. Тесты Godot входят в этап до коммита. Браузерные тесты/сборку при этом переносе не запускаем по решению владельца. Каждый успешный этап — короткий русский коммит; полезный урок — в `shareness/lessons.md`, изменения для игрока — в раздел «## Для игрока» описания PR (файла `CHANGELOG.md` больше нет).

## Основания решений

- [Godot: scene organization](https://docs.godotengine.org/en/stable/tutorials/best_practices/scene_organization.html): небольшие классы, слабые связи и внедрение контекста со стороны родителя. Наш ручной DI следует этой рекомендации.
- [Godot: Resources](https://docs.godotengine.org/en/stable/tutorials/scripting/resources.html): ресурсы описывают данные и могут разделяться между экземплярами. Поэтому runtime-состояние создаётся отдельно.
- [Godot: general optimization](https://docs.godotengine.org/en/stable/tutorials/performance/general_optimization.html): измерять узкие места и проверять эффект изменений. Поэтому производительность фиксируем отдельно от архитектурной чистоты.

Конкретные границы модулей, очередь команд и отказ от большого фреймворка — решения для этого проекта, а не обязательный стандарт Godot.
