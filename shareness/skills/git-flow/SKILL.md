---
name: git-flow
description: Ветки, коммиты, Pull Request и слияние в main. Применять при каждом пуше и PR.
---
1. Перед работой над кодом просмотри открытые issues (`gh issue list --state open`). Подходящая есть — бери её. Нет — создай (`gh issue create`) и только потом начинай.
2. Одна задача (issue) — одна ветка и один PR. В описании PR строка `Closes #N` (или `Fixes`/`Resolves`): issue закроется сама при слиянии в `main`, руками её не закрываем; без этой строки краснеет `pr_check.cjs`. Несколько задач в одном PR не собираем.
3. Работай в своей ветке, не в `main`. Имя по смыслу (`godot-world-time`, `companion-vikenty`). В `main` напрямую не пушит никто; свою ветку пушь сколько угодно (`git push -u origin <ветка>`), ИИ может делать это сам, не спрашивая.
4. Раздел «## Для игрока» в описании PR (навык `changelog`). Перед пушем можно гонять отдельные проверки из `build-and-test`, но итог — шаг 6.
5. Коммит: короткое русское описание, что изменилось.
6. В `main` — только через Pull Request из ветки (`gh pr create --base main`). **Работа над PR закончена — ИИ сам запускает `node godot/tools/pr_check.cjs`** (навык `build-and-test`, п. 8), не дожидаясь просьбы: каждый ИИ на ПК своего человека. ИИ в облаке без Windows ставит «ожидает», полный прогон делает ИИ на ПК автора. После каждого нового пуша — снова. Сливает Глеб, когда на последнем коммите зелёный `local/pr-check`. Если `main` ушёл вперёд и появился конфликт, перенеси ветку на свежий `main` (`git rebase origin/main`), реши конфликт и запушь ветку заново.
7. Не сливай в `main` то, что ломает игру, сохранения или тесты, и то, что меняет игру целиком (другая эпоха, жанр, огнестрел вместо средневековья), без явного «да» Глеба (см. «Жёсткие правила» в `CLAUDE.md`).
